# 02 · 安全与回滚

造数一旦删错存量真实数据，代价极高。本文记录 ID 分配、写前预检、台账格式与
purge 语义——**改动 simulator.py 时不要绕过这三层防护**。

## 一、ID 分配：IdPool

`IdPool.SPEC` 按实体类型给定 `(起始值, 步长)`，形态贴近真实库（长度、前缀）：

- 12 位：`cntrl_sta 990000000001`
- 11 位：`cust / bp / settle / rcvbl 99000000001`
- 9 位：`pipeline / adj_volt 990000001`
- 16 位设备类：`dev / meter_run 8199000000000001`（前缀 8199，与真实 8100 区分）
- 32 位受限：`app 1800000000`、`sch 1810000000`（目标列为 `int(32)`）

### 紧凑 ID 空间

`dwd_` 层沿用了源系统的 **32 位 int 外键列**（如 `dwd_cst_bus_app_form.cust_id`、
`dwd_cst_inst_elec_sch.inst_id`），装不下 `dim` 层的 bigint 主键。处理方式：

- 检测到存在 32 位关联列时，切换到**紧凑 ID 空间**：`_alloc_window()` / `_scan()`
  从候选起点（`200000000`、`1000000000` …）向内寻找一段与存量无重叠的窗口，
  使所有计数器都落在 `int32` 范围内。
- 备用的 `_coerce()` 会把超界值置 NULL 并记入 `nulled`，但**这会造成关联断裂**，
  仅作为兜底；正常运行应保证 0 列置空（报告里会打印）。
- 两个跨表复用的计数器必须拆开：`rela`（变电站↔线路）与 `rela_ds`（线路↔台区）
  各用一个计数器，否则会在两张关系表间撞主键。

## 二、写前预检：preflight()

`_seed_ids(n_counties)` 先按目标库各关联列的**实测 MAX** 抬升所有计数器起点，并
为每个计数器扫描空闲窗口；随后 `preflight()` 逐个确认"ID 窗口与存量数据零重叠"，
有重叠立即报错、拒绝写入。输出：

```
[ID] 已为 30 类计数器分配安全 ID 窗口
[预检] 16 类计数器 ID 窗口均与存量数据无重叠，可安全写入
```

## 三、主键清单台账

每轮生成把**实际插入的每一行主键**写入本地 JSON（**不写业务库任何表**）：

```
scripts/manifest/{db}__{tag}__{stamp}.json
{
  "tag": "模拟", "db": "fz01",
  "ym_from": 202506, "ym_to": 202510,
  "created_at": "2026-09-12 18:09:05",
  "tables": {
    "dim_cst_cust": {"pk": "cust_id", "rows": 1920, "count": 1920, "pks": [200000001, ...]},
    "dwd_cst_es_meter_energy_day_l_xz": {"pk": "meter_asset_no", "rows": 900000, "count": 1400, "pks": [...]},
    ...
  }
}
```

`rows` = 本轮写入行数，`count`/`pks` = **去重后**的主键集合（删除按集合执行，
去重不改变语义；日电量这类表逐日重复同一主键，去重后台账体积降一个数量级）。

写入策略：每完成一个区县，`flush()` 落库后覆写一次同一文件（路径在首次写入时
生成并缓存，一轮内复用）；采用 `写 .tmp → os.replace()` 原子替换。**崩溃时文件里
就是"已落库的那些行"，可完整回滚。**

- 主键列由 `ID_COLS[表][0]` 推断，调用方也可显式传 `pk=`。
- 若某表写了却没登记主键，报告出现 `[回滚缺口]` 告警 —— 必须补齐 `ID_COLS`，
  否则 purge 会漏删。

## 四、purge 语义

```
python simulator.py --purge --tag 模拟 --dry-run   # 预览：匹配台账 + 每表拟删数
python simulator.py --purge --tag 模拟             # 执行
```

- 扫描 `manifest/` 下文件名匹配 `{db}__{tag}__*.json` 的全部台账，**合并**其中的
  主键集合（同一 tag 多轮生成也能一次清干净）。
- 逐表 `DELETE FROM t WHERE pk IN (%s,...)`，每 1000 个一批；删除前
  `SET FOREIGN_KEY_CHECKS=0`（库内当前无外键，仅作兜底）。
- 执行后把已消费台账改名为 `*.purged` 归档（不删除，便于追溯/重放）。
- 因 tag 参与文件名解析，**tag 不得包含 `__`**。

### 为什么不用 ID 区间

早期版本登记的是 `(表, 列) → [min, max]` 区间，删除时 `col BETWEEN min AND max`。
问题：区间跨轮次用 LEAST/GREATEST 累积后，会把**真实数据**圈进来，导致误删
（曾造成 `dim_cst_cntrl_sta 9→0`、`dim_cst_cust 30→6` 等）。主键清单方案下，
删除的每一行都是"本次确实插入过的行"，从原理上杜绝此类事故。**不要回退到区间。**

## 五、安全自测流程（改动生成/回滚逻辑后必做）

```bash
# 1) 全库行数基线
python snapshot_counts.py before.json

# 2) 小批生成
python simulator.py --counties 2 --from 202508 --to 202510 --daily recent --tag selftest

# 3) 质量体检
python validate.py --tag selftest

# 4) 回滚并复核：再快照一次，行数须与基线**逐表一致**
python simulator.py --purge --tag selftest
python snapshot_counts.py after.json
# 比对 before.json / after.json：差异表数应为 0
```

判定标准：`purge` 后全库行数与基线**差异表数 = 0**。达标即回滚机制安全。

**已实测结论**（2026-09-12，`database01`，基线 71,992 行 / 120 表）：

| 场景 | 写入 | purge 后 | 差异表数 |
|---|---|---|---|
| 小批 2 区县 short 账期 | 5,652 | 71,992 | 0 |
| 单区县长账期（`--daily full`） | 25,952 | 71,992 | 0 |
| 全量 96 区县 | 见生成报告 | 71,992 | 0 |

注意第二行：**即使生成过程异常中断**，台账里已登记的 25,952 行仍被完整删除、
精确回到基线——因为台账每完成一个区县就原子覆写一次。这是"崩溃也能回滚"的实证。

### 圈定仿真范围的正确姿势

体检/统计要回答"仿真数据有没有问题"，前提是**只圈住仿真行**。真实库里有若干
占位/样例数据与仿真数据同表共存：

| 表 | 占位数据特征 |
|---|---|
| `dwd_cst_a_ll_dist_det_day` | `pro_mgt_org_code='33101'`，803 行，`rec_id` 在 5.5 亿区间 |
| `dwd_cst_es_e_mp_comp_curve_h` | `cust_no='000022'`，216 行，`tv=100/ta=10` 恒定 |
| `dwd_cst_proc_acct` / `ads_*` | 同样出现 `mgt_org_code='33101'` |

仿真行的特征：`rec_id`/`id` 落在 9.9 亿以上区间、名称带 `--tag`、`mgt_org_code`
是真实区县码。**凡是按弱键（`cust_no` 之类可能重号）圈定，就会把占位数据算进来，
误判成"仿真数据有缺陷"。** 正确做法是一路回溯到强键：

```
tag 名称 → dim_cst_inst_elec_cons.inst_id → dwd_cst_meter_run.meter_asset_no
                                       → dwd_cst_inst_bilg_card.bilg_card_id
                                       → dwd_cst_rcvbl_acct / dwd_cst_addl_charg ...
设备域：dim_cst_cntrl_sta.resrc_supl_name LIKE '%tag%'
        → pms_cntrl_sta_id → PMS 站 PSR → pwline_id → 配变 → 关系表
D5000 模型：id 第 4~9 位 adcode IN (本方 adcode 集)
```

**另一类坑**：不要对含 `LIKE '%xx%'` 的 SQL 做 `''.replace('%s', str(ym))` 拼接。
tag 以 `s` 开头时，`'%smoke%'` 里首个 `%` 紧跟 `s` 会被当成 `%s` 占位符替换掉，
条件变成 `'202510smoke%'`，**全部查空却不报错**。账期应直接内联进 f-string。

### 体检性能：先物化，再校验

真实库的业务表**只有主键、没有任何二级索引**（表结构如此，不要为了体检去 ALTER 它）。
在这种库上写"关联子查询"会退化成逐行全表扫描：80 万行加收明细的对账查询实测跑了
**9 分钟仍未结束**。`validate.py` 的处理方式是：

1. 把圈定集合物化成**带索引的临时表**（`_sim_inst` / `_sim_bilg` / `_sim_meter` …）；
2. 把"被反复比对的大表"也物化一次（`_addl` / `_addl_agg` / `_hxz` / `_curve` …）；
3. 之后所有校验都只查临时表，避免相关子查询。

效果：全套体检 **20 秒**完成，结论与慢查询版逐项一致。

两个必须注意的细节：

- **MySQL 不允许同一查询里两次引用同一张临时表**（`ERROR 1137 Can't reopen table`）。
  因此要**逐层物化**：先 `_addl`，再由它 `GROUP BY` 出 `_addl_agg`，最后用
  `_sim_bilg LEFT JOIN _addl_agg` 做对账，每张临时表在每条 SQL 里只出现一次。
- 临时表建索引时，**TEXT 列在联合索引里必须带前缀长度**
  （`ADD INDEX k (meter_asset_no(24), data_date(19))`），否则报
  `ERROR 1170 BLOB/TEXT column used in key specification without a key length`。
