# 01 · 仿真模型

本文说明"造什么、怎么造、勾稽怎么闭合"。所有取值来自 `profiles.json`（真实库反向
勘探）与 `simulator.py` 顶部的业务经验参数，二者叠加。

## 一、生成根节点：区县供电公司

`profiles.json.counties` 来自真实库 `dim_org_region_map` 中 `org_level='区县'` 的
组织（当前 96 个），每个区县独立生成一套完整"供电单元"，其 `mgt_org_code` 即为该
区县编码。名称统一带 `--tag`（默认 `模拟`），用于识别与校验。

## 二、电网拓扑（主数据）

每个区县按如下固定结构生成，层级关系写入关系表：

```
dim_cst_cntrl_sta   (220kV 变电站，电压 交流220kV)
        │  dim_cst_cntrl_sta_pline_rela
dim_cst_pipeline    (110kV 线路)
        │  dim_cst_cntrl_sta_pline_rela
dim_cst_cntrl_sta   (110kV 变电站，电压 交流110kV)
        │  dim_cst_cntrl_sta_pline_rela
dim_cst_pipeline    (10kV 线路 ×2)
        │  dim_cst_pline_dist_sta_rela
dim_cst_dist_sta    (10kV 台区 ×3~5)
        └─ dim_cst_adj_volt_dev (配电变压器，与台区 1:1)
```

- 容量档：220kV ∈ {120000,150000,180000,240000} kVA；110kV ∈ {40000…120000}；
  台区配变 ∈ {100…1600}（见 `CAP_220 / CAP_110 / CAP_DIST`）。
- 电压描述分档与真实库 `code_value_items.voltage_desc` 对齐：
  `交流220kV / 交流110kV / 交流35kV / 交流10kV / 交流380V / 交流220V`。

## 三、客户侧（主数据，约 20 户/区县）

一户一条链，实体与关键字段：

| 表 | 主键 | 说明 |
|---|---|---|
| `dim_cst_business_partner` | `bp_id` | 业务伙伴，名称 `{区县简称}{tag}用户NN` |
| `dim_cst_cust` | `cust_id` | 客户 |
| `dim_cst_elec_cons_cust` | `elec_cons_cust_id` | 用电客户 |
| `dim_cst_settle_acct` | `settle_acct_id` | 结算账户 |
| `dim_cst_cust_agrt` | `cust_agrt_id` | 供用电合同/协议 |
| `dim_cst_inst_elec_cons` | `inst_id` | 用电计量点（挂客户/台区/线路/变电站） |
| `dim_cst_dev` | `dev_id` | 电能表设备台账 |
| `dim_cst_elec_meter` | `dev_id` | 电能表计量属性（倍率、接线、精度等） |
| `dwd_cst_meter_run` | `meter_id` | 计量点运行（表计与计量点/客户绑定，含 asset_no） |

- 客户分三类：`低压居民 / 低压非居民 / 高压`，类别占比取自
  `profiles.json.customer.categ`（加权）。
- 综合倍率：低压直抄 `RTO_LOW=[1]`；高压经互感器 `RTO_HIGH=[30…10000]`。
- 电价按用电类别映射（`PRICE` 字典），用于**电量→电费**勾稽。

## 四、业务数据链条（2025 年至今，逐月）

对每个客户、每个账期 `ym`（`ym_range(--from, --to)`）生成：

```
1) dwd_cst_mr_data            抄表：上期/本期读数、抄见量
2) dwd_cst_inst_bilg_card     计费卡：总结算量/费、目录电费、加收、五段电量
3) dwd_cst_sgmt_qty_charg     分段量费：高压 3 段（尖/峰/谷），低压 1 段
4) dwd_cst_rcvbl_acct         应收：ec_qty / rcvbl_amt
5) dwd_cst_rcvbl_addl_acct    应收加收明细（加收>0 时）
6) dwd_cst_charg_acct         交费流水（charg_amt）
7) dwd_cst_rcvd_acct          实收（rcvd_amt）
8) dwd_cst_acct_bal           账户余额快照
```

逐日：`dwd_cst_es_meter_energy_day_l_xz`（低压表）/ `dwd_cst_meter_energy_day_h_xz`
（高压表），按 `--daily` 决定覆盖月份。另生成业扩（`bus_app_form → acc_sch →
meter_sch → wk_order → step_rec → proc_acct`）、装拆移换、退补单等。

### 关键勾稽公式（引擎保证，`validate.py` 复核）

| 关系 | 实现 |
|---|---|
| 月电量 | `_monthly_qty`：按类别基准 × 容量 × 季节系数(浙江口径 7-9月迎峰) × 随机 |
| 目录电费 | `t_ctlg_exp = deg_exp = round(qty × price, 2)` |
| 加收 | `t_addl_charg = round(deg_exp × U(0, 6%), 2)` |
| 总结算费 | `t_settle_exp = t_ctlg_exp + t_addl_charg` |
| 总结算量 | `t_settle_qty = int(qty)` |
| 分段闭合 | `settle_qty_02+03+04 = tot_q`（先取整前两段、余额给第三段，**保证 int 之和==int(总)**） |
| 应收 | `ec_qty = int(qty)`；`rcvbl_amt = t_settle_exp` |
| 实收 | `charg_amt = rcvd_amt = round(t_settle_exp × pay_ratio, 2)`，94% 足额、其余部分/延期 |

## 五、设备域（PMS 配电台账 + D5000 电网模型）

真实库里"营销域看到的设备"只有 `dim_cst_*` 这一层，配电设备本体在 **PMS** 侧、
电网拓扑模型在 **D5000** 侧。要把 120 张表补全，必须生成这两块，并让它们与营销域
**用同一个 ID 串起来**。

### 5.1 跨域桥接（最重要）

`dim_cst_cntrl_sta.pms_cntrl_sta_id` 与 `dim_cst_pipeline.pms_pipeline_id` 是营销域
指向设备域的两个外键。真实库里这两个字段是**断的**（样本 14 行 0 命中），仿真里
必须接上，否则跨域 JOIN 永远为空：

```
dim_cst_cntrl_sta.pms_cntrl_sta_id = dim_equ_t_p_pd_stationpsr.id
dim_cst_pipeline.pms_pipeline_id   = dim_ast_t_p_pd_feederlinepsr.id
```

PMS 主键是**文本**形态：`{8 位类型前缀}-{9 位流水}`，例如 `30000000-990000034`。
流水号由独立的尾号计数器分配（起点 ~990000001），与营销域的 bigint 完全隔离。

### 5.2 PMS 设备内部关联

| 关系 | 字段 |
|---|---|
| 馈线 → 起点变电站 | `feederlinepsr.start_station_id` = 站 PSR id |
| 支线/电缆段 → 馈线 | `parent_id` / `root_id` = 馈线 PSR id |
| 配变 → 馈线 | `pdzn_transformerpsr.pwline_id` = 馈线 PSR id |
| 台区 PSR → 配变 | `dy_stationzonepsr.power_psr_id` |
| 配变↔馈线关系 | `rel_pdtransformer_feederline.{transformer_psr_id, feeder_psr_id, line_psr_id}` |
| 公变台账 | `rel_transformer_publ.dev_id` = 配变 PSR id（`cons_no` 回指客户） |
| 专变台账 | `rel_transformer_priv.dev_id` = 专变 PSR id（`cons_no` 回指客户） |
| 杆塔 | `polesitepsr.parent_id` = 馈线 PSR id |

设备表里的 `district / depart / section / maintenance_team / dev_master` 是 32 位
十六进制组织码，真实库如此。仿真用 `md5(org_code + 角色后缀)` 确定性生成，
**同一区县稳定、跨区县可区分**，不要改成可读字符串。

### 5.3 D5000 电网模型

10 张 `dim_grid_*` / `dwd_grid_*` 表用**原生编码 ID**，不占用 IdPool：

```
id = {3 位表类型码}{6 位区县 adcode}{9 位流水}
例：121330102000000001 → 表类型 121，adcode 330102（杭州上城），流水 1
```

- 表类型码见 `GRID_PREFIX`（如 `acline_b=121`、`busbar_b=130`、`breaker_b=132`）。
- `adcode` 取真实区县行政区划码（`3301xx`），而真实库样本用的是 `0/1` 前缀占位码
  （`033000`），**天然不冲突**；写前 `preflight_native_grid()` 仍会逐个校验。
- 电网模型是**地区级**的（一个地区一套），因此按"地区"而非"区县"生成，
  已存在真实主键的地区跳过不写，只补缺失地区。

### 5.4 D5000 ↔ 营销/设备专业：只有"地区级"能通，**设备级打不通**

这是被反复问到的问题，实测结论如下（2026-09-12 核验）。

**设备级（device-level）—— 不通，缺"设备身份映射"环节：**

| 候选键 | 实测结果 |
|---|---|
| D5000 `st_id` / `dev_id` / `line_id` 指向 PMS PSR id | ❌ 真实数据里大量是 `2147483647`（= NULL 哨兵），且值域是 D5000 自己的命名空间 |
| PMS ↔ D5000 的 ID 编码互映 | ❌ 两套独立编码：PMS `{8位前缀}-{9位尾号}` / MRID `11M0000…`；D5000 `{3位类型码}{6位adcode}{9位流水}` |
| 名称匹配 | ❌ 两侧名字都**脱敏**：D5000 如 `裘*江变`，营销侧真实行整个是 `***` |
| 设备 PSR `georegion` ↔ D5000 `region` | ❌ `georegion` 是 UUID（`4c549d40-4054-11e7-…`），不是 adcode，交集 **0** |
| 反查：营销/设备侧是否有 D5000 语义列 | ❌ 全库 `dim_cst_* / dwd_cst_* / dim_equ_* / dim_ast_*` **无任何** `d5000/dispatch/grid` 语义字段 |
| 反查：D5000 表内是否有 PMS 形态取值（`30000000-%` / `11M%`） | ❌ 17 张表全部文本列扫描，**0 列命中** |

> 本体库口径也印证这一点：`ontology_relations` 里 120 条 grid 相关关系，
> **全部是 D5000 内部互连或 `ads_grid_* → dim_cst_mgt_org`（机构码）**，
> 没有一条连到 `dim_equ_*` / `dim_ast_*` / `dim_cst_cntrl_sta` / `dim_cst_pipeline`。
> 但 `ontology_entities` 把两者归进了**同一实体**（电网厂站 / 电网线路 / 电网变压器 /
> 电网一次设备），即"语义上是同一批物理设备的两套记录，但物理层缺映射表"。

**地区级（region-level）—— 能通，这是当前唯一可用的关联路径：**

```
D5000 设备 ──adcode──→ dim_org_region_map.region_adcode ──→ mgt_org_code ──→ 营销全域
```

`dim_org_region_map` 是机构码 ↔ 行政区划码的权威映射（3,354 行，覆盖省 31 / 市 361 / 区县 2,955）。

| D5000 表 | 取 adcode 的字段 | 命中率 |
|---|---|---|
| `con_substation_b` | `region` | 12 / 13（唯一天窗：`青*云变` 用撤市设区旧码 `330185`，未在映射表里） |
| `dwd_grid_t_ts_sg_da_feederline_b_new` | `RIGHT(grid_id, 6)` | 291 / 292 |
| `dim_grid_t_ts_sg_da_acline_b` | `owner` | 312 / 312 |
| `dim_grid_t_ts_sg_da_breaker_b` 等一次设备 | 先 `st_id` → 站 → `region` | **真实数据 0**（`st_id` 为哨兵值）；仿真数据可通 |

标准写法（注意 `region` 是 int，要 `CAST` 成字符再比）：

```sql
SELECT m.mgt_org_code, m.region_name,
       COUNT(DISTINCT f.id)            AS d5000_feeder,
       COUNT(DISTINCT d.dist_sta_id)   AS mrk_dist_sta,
       COUNT(DISTINCT i.inst_id)       AS mrk_inst
FROM dwd_grid_t_ts_sg_da_feederline_b_new f
JOIN dim_org_region_map m ON m.region_adcode = CAST(RIGHT(f.grid_id, 6) AS CHAR)
LEFT JOIN dim_cst_dist_sta d        ON d.mgt_org_code = m.mgt_org_code
LEFT JOIN dim_cst_inst_elec_cons i  ON i.mgt_org_code = m.mgt_org_code
GROUP BY m.mgt_org_code, m.region_name;
```

因此仿真侧刻意让 D5000 的 `region` / `owner` / `grid_id` 全部内嵌**真实 adcode**
（而不是真实库样本里的 `033000` 占位码）：**仿真数据 11/11 站、288/288 馈线、
288/288 线路 100% 可经地区码打通到机构与营销数据**。

> 若将来要做"设备级"贯通，缺的不是仿真，而是一张
> **设备身份映射表**（PMS PSR id ↔ D5000 id ↔ MRID ↔ 营销资产号）。
> 在没有这张表之前，任何试图按 ID 直连 D5000↔设备的 JOIN 都会返回空集。

## 六、派生业务明细

月度量费闭环之外，还有一批"明细/过程"表，价值在于让问数场景能跨表追问。

| 表 | 生成口径 |
|---|---|
| `dwd_cst_addl_charg` | 拆两条（政府性基金 / 其他），`SUM(addl_amt)` 严格等于计费卡 `t_addl_charg` |
| `dwd_cst_special_expense` | 力调电费，仅高压客户，`settle_exp = 月电量 × U(-0.013, 0.013)` |
| `dwd_cst_a_ll_dist_det_day` | 台区供电量 `= Σ该台区用户日电量 / (1 - 线损率)`，线损率 U(3%, 8%) |
| `dwd_cst_es_meter_energy_day_p` | 复用同一批日电量，保证与 `_l_xz` / `_h_xz` 同源同值 |
| `dwd_cst_es_e_mp_comp_curve_h` | 96 点**有功功率**：把日电量拆 96 段再 ÷0.25h |
| `..._curve_h_a` / `..._curve_h_v` | A 相电流（由功率反算再按 CT 折算）/ 电压（PT 二次） |
| `dwd_cst_invest_order` 等 | 投资工单/附属材料/设备领用，挂到业扩申请单 `bus_app_form_id` |
| `dwd_cst_gc_app_rec` / `_conn_gen_power_app` | 分布式光伏并网申请，挂客户 |

### ⚠️ 曲线表的 `tv` / `ta` 不是电量

这是最容易搞错的地方。按本体库 `schema_column_docs` 的字段口径：

- `tv` = **电压变比**（PT 变比），高压计量典型值 `100`
- `ta` = **电流变比**（CT 变比），典型值 `1/2/3/4/5/6/10/15/20/30/40/50/75/100`
- `p1..p96` = **功率**（15 分钟平均有功，kW），不是电量

因此恒等式是 **`Σp1..p96 × 0.25h = 该表当日电量`**，而不是 `Σp = 电量`。

变比建模：低压直通 `pt=1, ct=1`；高压 80% 高供高计（`pt=100`）、20% 高供低计
（`pt=1`）。先定 `pt/ct` 再算 `comp_rto = pt × ct`，这样
`dim_cst_elec_meter.self_rto = ct`、`dwd_cst_meter_run.comp_rto`、曲线表 `tv/ta`
四处天然自洽。

## 七、刷新真实分布

库结构或数据变化后，重新勘探：

```bash
python profile_db.py --db fz01        # 覆盖写 references/profiles.json
```

会重新采集：区县清单、电压等级分布、容量档、倍率档、电价码、用电类别占比、
ID 形态（长度/前缀）、业务账期范围等。**先刷新再跑仿真**，可让仿真跟随真实库演进。
